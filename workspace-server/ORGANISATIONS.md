# DuckBio Workspace organization administration
The server-side `organization-store.mjs` enforces app-specific seat limits and individual user roles in SQLite. Roles come from the existing six-app policy. Organizations are isolated; assigning roles consumes only that app's purchased seats. The last organization administrator cannot be removed.

**Purchases are not active.** `applyVerifiedSeatPurchase` is an internal method for a future server-side, signature-verified billing adapter. No browser API can increase seats. Single, Mixed and Bundle selections are validated and purchase references are idempotent. Do not call this method from an untrusted HTTP handler.

This store does not create central identity accounts, process payments, send invitation emails, or modify native app permissions. It is a tested backend building block; those links require separate reviewed integrations. No production/customer data is involved.

## Operator-only first organization setup

After creating the private central administrator with `shared-auth/manage-identity.mjs`, the server operator can register an organization in the **private** Workspace database:

```bash
node setup-organization.mjs --identity-db /srv/private/identity.sqlite --organization-db /srv/private/organizations.sqlite --id lab-1 --name "Example Lab" --owner-id <existing-verified-account-uuid> --nickname Admin
```

The CLI reads the existing identity database **read-only**, requires the exact account ID to be an active central administrator, and refuses aliases into public web directories. A transaction creates the organization and its first admin membership, with **zero purchased seats and zero native app roles**. Only a separate signature-verified billing service may add seats. Never expose this operator command as an HTTP API and never print account, email or database secrets in logs. Synthetic tests verify this flow and rejection of member accounts/duplicate organizations.

## Organization invitations and removing users

The organization administrator can create a seven-day, one-use invitation to their **currently selected organization**. The API stores only a SHA-256 digest of its random 256-bit token. The administrator receives a private invitation URL for secure manual sharing; **email delivery is not connected**. An existing DuckBio account must sign in with the exact invited email, while a new recipient can create a password and central member identity when accepting the invitation. Invitations grant organization membership only, **zero app roles and zero seats**. Native app access is not inferred from email or organization membership.

The **Remove** control removes the user's membership and all their Workspace app-role/permission assignments in that organization. It does not delete central identity or any other organization's memberships or application data. The final organization administrator cannot be removed. Session-bound organization checks fail closed if membership is removed.

This is isolated preproduction source; no mail or billing integration, production account cutover, actual app role enforcement or deployment has occurred. All invite links are bearer credentials: deliver them privately and avoid posting in tickets or public chat.

## Subscription drafts

The admin's Subscriptions tab shows paid/assigned per-app seat counts from private SQLite, and allows a selected-organization admin to create and cancel **unpaid subscription drafts** for valid Single (one app), Mixed (two–five apps) or Bundle (six apps) selections with a common positive seat quantity. These draft records are durable and tenant-isolated. They are not invoices, Stripe subscriptions, orders, or granted licences; creating/canceling one never calls `applyVerifiedSeatPurchase` or updates seat counters. To buy or change a paid subscription, a signed, idempotent Stripe checkout/webhook and billing reconciliation integration is still required, followed by staging tests. **Do not call the draft flow a completed purchase.**

## Optional automatic invitation email

Manual invitation links are used unless **both** `SUITE_RESEND_API_KEY` and `SUITE_INVITATION_FROM` are configured in the private Workspace broker environment or `SUITE_ENV_FILE`. The sender (e.g. `DuckBio <support@your-verified-domain.example>`) must be verified with Resend; use a real receiving address and proper SPF/DKIM/DMARC. Secrets must never be committed or placed in the public `development/docs` website. When configured, the broker sends a plain-text invitation with a hashed idempotency key. A successful provider API acknowledgement returns `delivery: email` to Workspace without exposing the bearer link. If the provider times out or rejects it, the pending invitation is revoked and its seat reservation freed. This can result in a delivered but unusable link on ambiguous timeouts; the admin can invite again. **Provider acceptance is not a guarantee of inbox delivery.** Automated tests never send live emails. No live provider or production origin has been configured.

## Stripe test Checkout adapter (not yet connected to UI)

The isolated `stripe-test-checkout.mjs` adapter accepts only a private `sk_test_` secret and an explicit plan/app-combination price map such as `{"Mixed:eel,goflo":"price_ACTUAL_TEST_PRICE_ID"}`. The price must be a preconfigured recurring Stripe test price with the intended plan discount; Workspace does not invent any amount. Every test Checkout request includes the exact draft/organization metadata and an idempotency key supplied by a future persistent checkout-intent store. It rejects live keys, unconfigured prices and non-Stripe redirect hosts. Unit tests use synthetic Stripe responses; no Stripe account, real payment, production integration or licensing activation has been configured. A durable intent and authenticated server checkout route are required before enabling any checkout UI.

## Test Checkout intent storage

`stripe_test_checkouts` is a private, transactional SQLite ledger keyed by the subscription draft ID. The first authenticated admin request pins a Stripe test Price ID and a deterministic idempotency key. Repeating the same request returns the same parameters, while changing the price fails. Saving the returned test-only Checkout URL is idempotent and checked against Stripe's checkout host. After a checkout attempt starts, the draft cannot be canceled through the draft UI (ambiguity about remote Stripe session). The ledger never issues purchased app seats or processes webhook payments. Existing drafts remain unaffected until a test checkout is explicitly initiated. Next: wire an authenticated checkout endpoint, then signed webhook reconciliation before any production billing.

## Signed Stripe webhook verification (test mode)

The `stripe-test-webhook.mjs` verifier accepts only private `whsec_` configuration, verifies the HMAC SHA-256 `Stripe-Signature` over the **original raw bytes** within a five-minute timestamp tolerance, rejects tampered/expired/live events and emits only event ID/type/object ID plus payload digest for durable idempotent recording. Do not parse/transform JSON before verification and never process success redirects as proof of payment. This is a security primitive only: the HTTP ingress and event ledger are now implemented, but full subscription reconciliation must still be implemented and tested before any entitlement activation, let alone live billing.

## Durable Stripe test webhook event ledger

The private organization SQLite database now stores only **verified webhook event metadata** (event ID, type, object ID, timestamp, digest, and any matched local draft/organization). Replays of an identical event ID and digest are idempotent across restarts. Reuse of an event ID with different signed metadata is rejected. Unknown events are stored as unassigned, not attached to an unrelated tenant. Only an existing ready **test** Checkout session can be matched; a `checkout.session.completed` event still does **not** prove that an invoice is paid. No seat counters, subscriptions, app grants or native app accounts are changed. Full payment/subscription reconciliation remains a separate, mandatory step.

## Private Stripe test webhook HTTP endpoint

Only when private Workspace `SUITE_STRIPE_TEST_KEY`, `SUITE_STRIPE_TEST_PRICES_JSON`, `SUITE_ORGANIZATION_DB_PATH` **and** `SUITE_STRIPE_TEST_WEBHOOK_SECRET` are configured does the broker accept `POST /api/suite/billing/stripe-test-webhook`. Configuration missing the checkout/store dependencies fails startup; without the webhook secret, the endpoint returns 404. The `whsec_` secret belongs in the private environment, never in GitHub Pages or frontend code.

Stripe sends an unsigned browser session neither cookie nor CSRF token: this endpoint alone uses an HMAC SHA-256 over original raw bytes instead of browser authentication. Request host, method, JSON content type, timestamp (±5 min), signature, raw payload size (up to 64 KiB), and `livemode: false` are checked before the private SQLite ledger is written. Invalid signatures and malformed/oversized requests receive 4xx, and failed persistence returns 503 so Stripe can retry. Idempotent retries receive 200. The response `received: true` means **only that signed test metadata was stored**, never payment success. No event adds app seats or grants licenses.

This is not a public GitHub Pages feature and is not connected to a Stripe dashboard, live Stripe endpoint, deployed server, invoice verification, subscription reconciliation, or native app entitlements yet. Do not use a redirect query parameter, an email receipt, or merely `checkout.session.completed` to activate seats. All tests are synthetic and isolated from real services.

Out-of-order test webhooks are recorded as unmatched until an exact, valid test Checkout session ID is durably saved; the same transaction then links prior signed `checkout.session.completed` metadata to that draft's organization. A different session or organization is never inferred. This late association changes **metadata only**, not seats or payment status.

## Read-only test Stripe billing attestation

The isolated `stripe-test-reconcile.mjs` adapter makes three **server-side, test-key-only GETs** to Stripe: the previously pinned Checkout session, its subscription, and its latest invoice. It requires exact Checkout draft/organization metadata, subscription metadata, customer identity, one licensed subscription item with the pinned Price ID and purchased seat quantity, an active subscription, and a paid invoice with a positive amount, zero outstanding amount, paid timestamp and exact customer/subscription association. Unpaid or incomplete states stay pending; identity inconsistencies fail closed. It accepts either the newer invoice `parent.subscription_details.subscription` association or the older `invoice.subscription` field.

The adapter is deliberately **not connected to a browser route, background worker, webhook automatic processing, or licensing activation**. Its result is a read-only test attestation, not permission to call `applyVerifiedSeatPurchase`. Before issuing seats, the system still needs reconciliation persistence, subscription lifecycle and recurring billing handling, refunds/disputes, rechecks on changes, idempotent entitlement updates, and end-to-end staging tests. No real Stripe account or test dashboard is accessed by the synthetic CI tests.

## Admin-only test reconciliation API (opt-in)

The private broker only enables `POST /api/suite/organization/subscription/test-reconcile` when `SUITE_STRIPE_TEST_RECONCILE_ENABLED=true` is explicitly set alongside a private organization store, test Checkout key, and test price map. The request body is `{"organizationId":"selected-org","draftId":"existing-draft-id"}`. A signed-in **organization administrator** needs the selected organization and same-origin CSRF token. The backend reads only its own already saved and ready Checkout session/Price; clients cannot submit arbitrary Stripe session IDs. The server rechecks the live login, selected organization, admin membership, and pinned session after the read-only Stripe request. Pending and verified-paid-test statuses are returned to the admin but never treated as licenses.

This private diagnostic endpoint is not part of the public website or production payment experience. The result is **non-persistent** and may become stale immediately; it does not record a subscription, process renewals, activate seats, or grant permissions. Only synthetic fixtures are used in CI. A separate reviewed state machine, webhook/subscription processing, persistence, and revocation semantics are required before real billing.

## Durable test billing observations (not entitlements)

The private SQLite database now retains each explicitly requested administrator test reconciliation in `stripe_test_reconciliation_checks`, scoped to its subscription draft and organization. Each run begins as `checking` with a strictly increasing attempt counter and pins the locally saved test session/price. A new run makes any previous incomplete run `superseded`, preventing slower Stripe responses from overwriting newer observations. Successful checks are recorded as `pending` (with a short reason code) or `paid_test_verified`; unavailable Stripe reads are recorded as `unavailable`. The current test observation is returned in each admin subscription draft's `testReconciliation` field, including its check time, attempt number and `licensesGranted: false`. Earlier attempts remain available in the private database for audit; changes are also recorded in the organization-scoped audit log. Unexpected termination may leave `checking` as a stale observation until a subsequent admin-initiated check supersedes it.

The administrator's test-reconcile endpoint revalidates the authenticated admin, selected organization and pinned session after the network read, **then** stores its result transactionally. It returns the observation as well as the read-only Stripe result; transient provider failures return HTTP 503 after recording a non-authoritative `unavailable` status. There is no timer, recurring polling, background worker, payment capture, renewal scheduler, seat grant, permission update or live Stripe integration. Historical `paid_test_verified` means only that a test invoice appeared paid at that check time, not that a real subscription remains active or that Workspace may grant access. Subscription lifecycle and entitlement reconciliation remain separate future work.

## Administrator Stripe TEST billing status UI

When the existing private test reconciliation opt-in is enabled on the server, authorized organization administrators see a **Check Stripe TEST status** button beside their own ready Checkout drafts in the Subscriptions tab. The last persisted test observation and check time are displayed as text, with clear pending/unavailable/paid-test-only wording. This control stays hidden when test reconciliation is disabled, and each click makes a fresh server-side check (no browser access to Stripe keys). The status never authorizes app access or changes purchased/assigned seats. It is not a production billing UI and does not show a live subscription's entitlement status.

## Subscription renewal and cancellation observations (test mode only)

The server-side read-only Stripe TEST check now distinguishes the current subscription status (`active`, `past_due`, `unpaid`, `canceled`, `paused`, `trialing`, `incomplete` and `incomplete_expired`), scheduled cancellation at period end, and the latest invoice's billing reason (`subscription_create` for an initial invoice or `subscription_cycle` for a renewal). When Stripe supplies a billing-period end, prefer the subscription **item** period (newer Stripe API versions); fall back to the older subscription-level period. The exact Checkout/organization/customer/subscription/price/quantity link remains mandatory. A non-active status is always `pending`, even if the most recent invoice is paid. An active subscription whose latest invoice is not paid is also `pending`. A paid TEST invoice requires Stripe's paid flag and rejects invoices marked paid outside Stripe, in addition to the existing positive amount and timestamp checks.

Only a narrowly validated lifecycle summary is persisted under the newest private test reconciliation observation, so admins can see a renewal invoice or a scheduled cancellation when explicitly checking. Older observations safely show no lifecycle information. **This is not a renewal processor or entitlement state machine**: no Stripe subscription updates, automatic polling, payment retries, renewal grants, seat removal, native app revocation, or live-money flows have been added. A Stripe TEST subscription that appears active and paid at one instant never authorizes continued access without a separate reviewed and deployed billing-entitlement reconciler. Real Stripe account configuration and end-to-end payment testing remain outstanding.

## Selected-organization Stripe TEST check history

When the private TEST reconciliation feature is enabled, an organization admin can select **View TEST history** on an existing ready Checkout draft. The browser uses a same-origin, CSRF-protected `POST /api/suite/organization/subscription/test-history` endpoint scoped to the admin's session-selected organization and draft. Only the most recent 10 attempts are returned, newest first, with a small validated lifecycle summary. Internal Stripe session, invoice and subscription identifiers and original webhook data are never exposed. A failed, superseded or older paid-test observation must never be interpreted as a license or a reason to change access. This is a diagnostic timeline, not a background subscription reconciler.

## Stripe TEST seat projections and duplicate billing protection (no live licences)

After a completed administrator-initiated reconciliation, the private organization store maintains a **separate TEST seat projection** keyed by the existing subscription draft. A test-only candidate is generated only when Stripe's current subscription is active, its latest invoice is verified as paid **in Stripe**, and a validated billing period ends in the future. For a Single plan, the simulation assigns the draft quantity to one app; for Mixed and Bundle, the same seat quantity appears for each selected app. These counts are **never written to `seats.purchased`, `assignments`, `receipts` or native apps**, and they do not authorize any access.

Subsequent checks **replace** the same projection rather than add to it. Repeated observations of one invoice or a new renewal invoice on an existing subscription therefore do not double-count simulated seats. New private `stripe_test_subscription_bindings` and `stripe_test_invoice_refs` tables make the Stripe TEST subscription ID globally unique to one local organization/draft, and disallow an invoice ID from representing a second subscription or tenant. These integrity checks and the observation update run in the same SQLite transaction.

A canceled subscription produces `cancellation_review`, a past-due/unpaid subscription produces `payment_review`, incomplete Checkout produces `awaiting_payment`, and a failed remote check produces `unavailable`. The **projection count** then contains no candidate seats, but actual seats and member access remain unchanged; an unavailable check must not revoke users. A previously paid but now expired billing period is review-only. The Subscriptions UI keeps simulated seat candidates visually and semantically separate from real purchased seats and labels them *not purchased or activated*. Server-side aggregation is scoped to the currently selected organization.

This is NOT an entitlement engine. Before real billing, a separate reviewed migration must replace legacy additive receipts with subscription-based authoritative seats, define grace periods, reduce assigned seats safely, handle partial upgrades/downgrades/refunds/disputes and invoice ordering, integrate the six native apps, and pass end-to-end tests using an actual Stripe TEST account and staging backend. No production payment or user-license action occurs here.

## Read-only TEST seat transition impact and safe downgrades

Workspace also calculates a separate `testSeatImpact` diagnostic for administrators. It compares hypothetical TEST candidates with the existing per-app **assigned users plus reserved invitation seats**, and retains the real purchased seat count as a separately labeled reference. For an unambiguous, future-dated paid TEST candidate, a hypothetical shortfall is flagged as `assignment_conflict` if existing assignments plus invitations exceed the simulated seat quantity. For canceled, past-due, unavailable or expired TEST observations, it returns `manual_review` instead of recommending an automatic downgrade. Apps with no relevant TEST subscription have `not_evaluated`, never a zero-seat revocation instruction. The Subscriptions screen displays review warnings without changing membership, invitations, purchased seats or native app permissions.

This is **not** a command to enforce a reduction: the diagnostic sets `realSeatChanges: false` and `licensesGranted: false`. Production billing must separately define and test entitlements, grace periods, seat reservations, user notification and administrator-controlled resolution before any removal of existing access.

## Versioned shadow subscription entitlement ledger (no live effects)

The private database includes `subscription_entitlement_shadow`, an isolated, test-sourced record **keyed by Stripe TEST subscription ID**, with a unique organization/draft pairing and monotonic reconciliation revision. It is created **only after the original test subscription and paid invoice have been verified and linked**. A subsequent renewal of the same subscription replaces the record's revision and last paid invoice rather than creating additional licenses; a canceled, past-due or unavailable check replaces the recorded decision with a review-only state. All mutations occur inside the same SQLite transaction as the existing test observation. Prior invoices remain in the private test invoice-reference ledger for audit.

The pure `subscription-entitlement-planner.mjs` takes validated subscription records and organization app-seat assignments/reservations, and computes a **non-executing** per-app transition preview. It aggregates distinct subscription identities (not invoices), supports different app selections for Single/Mixed/Bundle, rejects duplicate subscriptions/foreign tenants/overflow, and reports `increase_candidate`, `unchanged`, `decrease_requires_review`, `assignment_conflict`, `manual_review`, or `not_evaluated`. Expired terms and unresolved states are never candidates. Every preview explicitly returns `realSeatChanges: false` and `licensesGranted: false`.

The shadow ledger does **not** update `seats`, `assignments`, `receipts`, authorization decisions or native apps. It is accessible only through private organization-store internals, not a public billing or purchasing route. It is preparation for a later reviewed production-entitlement migration, not its activation; there is no automated Stripe polling, real payment processing, app grant, cancellation, renewal or seat removal.

## Organization admin preview of shadow subscription transitions

The authenticated, CSRF-protected organization Subscriptions response includes `testEntitlementPlan` **only when the private Stripe TEST reconciliation feature is enabled**. It summarizes the read-only subscription shadow ledger for the administrator's selected organization: per-app simulated seat quantity, current real purchased seats, assigned users, invitation reservations and whether an increase is a candidate, a downgrade requires review, assignments exceed a hypothetical quota, or billing evidence is unresolved. The private Workspace Subscriptions screen displays this preview separately from real purchased seats and always states that no user access changes.

Unlike the legacy additive purchase model, the preview derives from unique subscription IDs and never treats repeat/renewal invoices as additional licenses. No new public route, Stripe API exposure, automatic user deactivation, seat write, app grant, or live billing authorization is created.

## Shadow entitlement inventory completeness (TEST only)

A paid-only shadow plan can omit Checkout sessions that have not yet produced a verified subscription. The additional private `testEntitlementReadiness` diagnostic therefore compares all **ready TEST Checkout drafts** with their test subscription shadow bindings before a manual reviewer interprets hypothetical subscription seats. It marks unbound Checkout sessions and subscriptions with unresolved or expired billing periods per app, and shows explicit review warnings in the administrator's Subscriptions page. `readyForManualPlanning` only means this **test-only diagnostic snapshot** has no detected missing or unresolved sources; it never authorizes activation or revocation of actual licenses. A provider outage or unverified payment always blocks readiness.

## Freshness guard for read-only Stripe TEST entitlement diagnostics

An earlier paid Stripe TEST check **cannot** be used as a current seat candidate while a more recent reconciliation is in progress, superseded, pending, or unavailable. The SQLite-backed TEST capacity estimate, subscription shadow planner, readiness report, review-impact report and per-draft seat preview all require the *latest* attempt to equal the stored candidate revision, have the `paid_test_verified` state, and have a completed timestamp not in the future or more than 24 hours old. The paid billing period must still extend beyond the current server time. Starting another check immediately invalidates the old positive candidate across all UI-facing summaries, including after a backend restart; a new verified paid check restores only a **test-only** candidate. Historical paid checks remain readable for auditing but never authorize actual seats. All legacy `seats`, receipts, invitations, assignments and native app access stay untouched. The 24-hour window is an intentionally conservative **diagnostic freshness limit**, not a Stripe payment or production license policy.
