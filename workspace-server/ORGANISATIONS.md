# DuckBio Workspace organization administration
The server-side `organization-store.mjs` enforces app-specific seat limits and individual user roles in SQLite. Roles come from the existing six-app policy. Organizations are isolated; assigning roles consumes only that app's purchased seats. The last organization administrator cannot be removed.

**Purchases are not active.** `applyVerifiedSeatPurchase` is an internal method for a future server-side, signature-verified billing adapter. No browser API can increase seats. Single, Mixed and Bundle selections are validated and purchase references are idempotent. Do not call this method from an untrusted HTTP handler.

This store does not create central identity accounts, process payments, send invitation emails, or modify native app permissions. It is a tested backend building block; those links require separate reviewed integrations. No production/customer data is involved.

## Operator-only first organization setup

After creating the private central administrator with `shared-auth/manage-identity.mjs`, the server operator can register an organization in the **private** Workspace database:

```bash
node setup-organization.mjs --identity-db /srv/private/identity.sqlite --organization-db /srv/private/organizations.sqlite --id lab-1 --name "Example Lab" --owner-id <existing-verified-account-uuid> --nickname Admin
```

The CLI reads the existing identity database **read-only**, requires the exact account ID to be an active central administrator, and refuses aliases into public web directories. A transaction creates the organization and its first admin membership, with **zero purchased seats and zero native app roles**. Only a separate signature-verified billing service may add seats. Never expose this operator command as an HTTP API and never print account, email or database secrets in logs. Synthetic tests verify this flow and rejection of member accounts/duplicate organizations.

## Organization invitations and removing users

The organization administrator can create a seven-day, one-use invitation to their **currently selected organization**. The API stores only a SHA-256 digest of its random 256-bit token. The administrator receives a private invitation URL for secure manual sharing; **email delivery is not connected**. An existing DuckBio account must sign in with the exact invited email, while a new recipient can create a password and central member identity when accepting the invitation. Invitations grant organization membership only, **zero app roles and zero seats**. Native app access is not inferred from email or organization membership.

The **Remove** control removes the user's membership and all their Workspace app-role/permission assignments in that organization. It does not delete central identity or any other organization's memberships or application data. The final organization administrator cannot be removed. Session-bound organization checks fail closed if membership is removed.

This is isolated preproduction source; no mail or billing integration, production account cutover, actual app role enforcement or deployment has occurred. All invite links are bearer credentials: deliver them privately and avoid posting in tickets or public chat.

## Subscription drafts

The admin's Subscriptions tab shows paid/assigned per-app seat counts from private SQLite, and allows a selected-organization admin to create and cancel **unpaid subscription drafts** for valid Single (one app), Mixed (two–five apps) or Bundle (six apps) selections with a common positive seat quantity. These draft records are durable and tenant-isolated. They are not invoices, Stripe subscriptions, orders, or granted licences; creating/canceling one never calls `applyVerifiedSeatPurchase` or updates seat counters. To buy or change a paid subscription, a signed, idempotent Stripe checkout/webhook and billing reconciliation integration is still required, followed by staging tests. **Do not call the draft flow a completed purchase.**

## Optional automatic invitation email

Manual invitation links are used unless **both** `SUITE_RESEND_API_KEY` and `SUITE_INVITATION_FROM` are configured in the private Workspace broker environment or `SUITE_ENV_FILE`. The sender (e.g. `DuckBio <support@your-verified-domain.example>`) must be verified with Resend; use a real receiving address and proper SPF/DKIM/DMARC. Secrets must never be committed or placed in the public `development/docs` website. When configured, the broker sends a plain-text invitation with a hashed idempotency key. A successful provider API acknowledgement returns `delivery: email` to Workspace without exposing the bearer link. If the provider times out or rejects it, the pending invitation is revoked and its seat reservation freed. This can result in a delivered but unusable link on ambiguous timeouts; the admin can invite again. **Provider acceptance is not a guarantee of inbox delivery.** Automated tests never send live emails. No live provider or production origin has been configured.

## Stripe test Checkout adapter (not yet connected to UI)

The isolated `stripe-test-checkout.mjs` adapter accepts only a private `sk_test_` secret and an explicit plan/app-combination price map such as `{"Mixed:eel,goflo":"price_ACTUAL_TEST_PRICE_ID"}`. The price must be a preconfigured recurring Stripe test price with the intended plan discount; Workspace does not invent any amount. Every test Checkout request includes the exact draft/organization metadata and an idempotency key supplied by a future persistent checkout-intent store. It rejects live keys, unconfigured prices and non-Stripe redirect hosts. Unit tests use synthetic Stripe responses; no Stripe account, real payment, production integration or licensing activation has been configured. A durable intent and authenticated server checkout route are required before enabling any checkout UI.

## Test Checkout intent storage

`stripe_test_checkouts` is a private, transactional SQLite ledger keyed by the subscription draft ID. The first authenticated admin request pins a Stripe test Price ID and a deterministic idempotency key. Repeating the same request returns the same parameters, while changing the price fails. Saving the returned test-only Checkout URL is idempotent and checked against Stripe's checkout host. After a checkout attempt starts, the draft cannot be canceled through the draft UI (ambiguity about remote Stripe session). The ledger never issues purchased app seats or processes webhook payments. Existing drafts remain unaffected until a test checkout is explicitly initiated. Next: wire an authenticated checkout endpoint, then signed webhook reconciliation before any production billing.

## Signed Stripe webhook verification (test mode)

The `stripe-test-webhook.mjs` verifier accepts only private `whsec_` configuration, verifies the HMAC SHA-256 `Stripe-Signature` over the **original raw bytes** within a five-minute timestamp tolerance, rejects tampered/expired/live events and emits only event ID/type/object ID plus payload digest for durable idempotent recording. Do not parse/transform JSON before verification and never process success redirects as proof of payment. This is a security primitive only: the HTTP ingress and event ledger are now implemented, but full subscription reconciliation must still be implemented and tested before any entitlement activation, let alone live billing.

## Durable Stripe test webhook event ledger

The private organization SQLite database now stores only **verified webhook event metadata** (event ID, type, object ID, timestamp, digest, and any matched local draft/organization). Replays of an identical event ID and digest are idempotent across restarts. Reuse of an event ID with different signed metadata is rejected. Unknown events are stored as unassigned, not attached to an unrelated tenant. Only an existing ready **test** Checkout session can be matched; a `checkout.session.completed` event still does **not** prove that an invoice is paid. No seat counters, subscriptions, app grants or native app accounts are changed. Full payment/subscription reconciliation remains a separate, mandatory step.

## Private Stripe test webhook HTTP endpoint

Only when private Workspace `SUITE_STRIPE_TEST_KEY`, `SUITE_STRIPE_TEST_PRICES_JSON`, `SUITE_ORGANIZATION_DB_PATH` **and** `SUITE_STRIPE_TEST_WEBHOOK_SECRET` are configured does the broker accept `POST /api/suite/billing/stripe-test-webhook`. Configuration missing the checkout/store dependencies fails startup; without the webhook secret, the endpoint returns 404. The `whsec_` secret belongs in the private environment, never in GitHub Pages or frontend code.

Stripe sends an unsigned browser session neither cookie nor CSRF token: this endpoint alone uses an HMAC SHA-256 over original raw bytes instead of browser authentication. Request host, method, JSON content type, timestamp (±5 min), signature, raw payload size (up to 64 KiB), and `livemode: false` are checked before the private SQLite ledger is written. Invalid signatures and malformed/oversized requests receive 4xx, and failed persistence returns 503 so Stripe can retry. Idempotent retries receive 200. The response `received: true` means **only that signed test metadata was stored**, never payment success. No event adds app seats or grants licenses.

This is not a public GitHub Pages feature and is not connected to a Stripe dashboard, live Stripe endpoint, deployed server, invoice verification, subscription reconciliation, or native app entitlements yet. Do not use a redirect query parameter, an email receipt, or merely `checkout.session.completed` to activate seats. All tests are synthetic and isolated from real services.

Out-of-order test webhooks are recorded as unmatched until an exact, valid test Checkout session ID is durably saved; the same transaction then links prior signed `checkout.session.completed` metadata to that draft's organization. A different session or organization is never inferred. This late association changes **metadata only**, not seats or payment status.

## Read-only test Stripe billing attestation

The isolated `stripe-test-reconcile.mjs` adapter makes three **server-side, test-key-only GETs** to Stripe: the previously pinned Checkout session, its subscription, and its latest invoice. It requires exact Checkout draft/organization metadata, subscription metadata, customer identity, one licensed subscription item with the pinned Price ID and purchased seat quantity, an active subscription, and a paid invoice with a positive amount, zero outstanding amount, paid timestamp and exact customer/subscription association. Unpaid or incomplete states stay pending; identity inconsistencies fail closed. It accepts either the newer invoice `parent.subscription_details.subscription` association or the older `invoice.subscription` field.

The adapter is deliberately **not connected to a browser route, background worker, webhook automatic processing, or licensing activation**. Its result is a read-only test attestation, not permission to call `applyVerifiedSeatPurchase`. Before issuing seats, the system still needs reconciliation persistence, subscription lifecycle and recurring billing handling, refunds/disputes, rechecks on changes, idempotent entitlement updates, and end-to-end staging tests. No real Stripe account or test dashboard is accessed by the synthetic CI tests.

## Admin-only test reconciliation API (opt-in)

The private broker only enables `POST /api/suite/organization/subscription/test-reconcile` when `SUITE_STRIPE_TEST_RECONCILE_ENABLED=true` is explicitly set alongside a private organization store, test Checkout key, and test price map. The request body is `{"organizationId":"selected-org","draftId":"existing-draft-id"}`. A signed-in **organization administrator** needs the selected organization and same-origin CSRF token. The backend reads only its own already saved and ready Checkout session/Price; clients cannot submit arbitrary Stripe session IDs. The server rechecks the live login, selected organization, admin membership, and pinned session after the read-only Stripe request. Pending and verified-paid-test statuses are returned to the admin but never treated as licenses.

This private diagnostic endpoint is not part of the public website or production payment experience. The result is **non-persistent** and may become stale immediately; it does not record a subscription, process renewals, activate seats, or grant permissions. Only synthetic fixtures are used in CI. A separate reviewed state machine, webhook/subscription processing, persistence, and revocation semantics are required before real billing.

## Durable test billing observations (not entitlements)

The private SQLite database now retains each explicitly requested administrator test reconciliation in `stripe_test_reconciliation_checks`, scoped to its subscription draft and organization. Each run begins as `checking` with a strictly increasing attempt counter and pins the locally saved test session/price. A new run makes any previous incomplete run `superseded`, preventing slower Stripe responses from overwriting newer observations. Successful checks are recorded as `pending` (with a short reason code) or `paid_test_verified`; unavailable Stripe reads are recorded as `unavailable`. The current test observation is returned in each admin subscription draft's `testReconciliation` field, including its check time, attempt number and `licensesGranted: false`. Earlier attempts remain available in the private database for audit; changes are also recorded in the organization-scoped audit log. Unexpected termination may leave `checking` as a stale observation until a subsequent admin-initiated check supersedes it.

The administrator's test-reconcile endpoint revalidates the authenticated admin, selected organization and pinned session after the network read, **then** stores its result transactionally. It returns the observation as well as the read-only Stripe result; transient provider failures return HTTP 503 after recording a non-authoritative `unavailable` status. There is no timer, recurring polling, background worker, payment capture, renewal scheduler, seat grant, permission update or live Stripe integration. Historical `paid_test_verified` means only that a test invoice appeared paid at that check time, not that a real subscription remains active or that Workspace may grant access. Subscription lifecycle and entitlement reconciliation remain separate future work.

## Administrator Stripe TEST billing status UI

When the existing private test reconciliation opt-in is enabled on the server, authorized organization administrators see a **Check Stripe TEST status** button beside their own ready Checkout drafts in the Subscriptions tab. The last persisted test observation and check time are displayed as text, with clear pending/unavailable/paid-test-only wording. This control stays hidden when test reconciliation is disabled, and each click makes a fresh server-side check (no browser access to Stripe keys). The status never authorizes app access or changes purchased/assigned seats. It is not a production billing UI and does not show a live subscription's entitlement status.

## Subscription renewal and cancellation observations (test mode only)

The server-side read-only Stripe TEST check now distinguishes the current subscription status (`active`, `past_due`, `unpaid`, `canceled`, `paused`, `trialing`, `incomplete` and `incomplete_expired`), scheduled cancellation at period end, and the latest invoice's billing reason (`subscription_create` for an initial invoice or `subscription_cycle` for a renewal). When Stripe supplies a billing-period end, prefer the subscription **item** period (newer Stripe API versions); fall back to the older subscription-level period. The exact Checkout/organization/customer/subscription/price/quantity link remains mandatory. A non-active status is always `pending`, even if the most recent invoice is paid. An active subscription whose latest invoice is not paid is also `pending`. A paid TEST invoice requires Stripe's paid flag and rejects invoices marked paid outside Stripe, in addition to the existing positive amount and timestamp checks.

Only a narrowly validated lifecycle summary is persisted under the newest private test reconciliation observation, so admins can see a renewal invoice or a scheduled cancellation when explicitly checking. Older observations safely show no lifecycle information. **This is not a renewal processor or entitlement state machine**: no Stripe subscription updates, automatic polling, payment retries, renewal grants, seat removal, native app revocation, or live-money flows have been added. A Stripe TEST subscription that appears active and paid at one instant never authorizes continued access without a separate reviewed and deployed billing-entitlement reconciler. Real Stripe account configuration and end-to-end payment testing remain outstanding.

## Selected-organization Stripe TEST check history

When the private TEST reconciliation feature is enabled, an organization admin can select **View TEST history** on an existing ready Checkout draft. The browser uses a same-origin, CSRF-protected `POST /api/suite/organization/subscription/test-history` endpoint scoped to the admin's session-selected organization and draft. Only the most recent 10 attempts are returned, newest first, with a small validated lifecycle summary. Internal Stripe session, invoice and subscription identifiers and original webhook data are never exposed. A failed, superseded or older paid-test observation must never be interpreted as a license or a reason to change access. This is a diagnostic timeline, not a background subscription reconciler.

## Stripe TEST seat projections and duplicate billing protection (no live licences)

After a completed administrator-initiated reconciliation, the private organization store maintains a **separate TEST seat projection** keyed by the existing subscription draft. A test-only candidate is generated only when Stripe's current subscription is active, its latest invoice is verified as paid **in Stripe**, and a validated billing period ends in the future. For a Single plan, the simulation assigns the draft quantity to one app; for Mixed and Bundle, the same seat quantity appears for each selected app. These counts are **never written to `seats.purchased`, `assignments`, `receipts` or native apps**, and they do not authorize any access.

Subsequent checks **replace** the same projection rather than add to it. Repeated observations of one invoice or a new renewal invoice on an existing subscription therefore do not double-count simulated seats. New private `stripe_test_subscription_bindings` and `stripe_test_invoice_refs` tables make the Stripe TEST subscription ID globally unique to one local organization/draft, and disallow an invoice ID from representing a second subscription or tenant. These integrity checks and the observation update run in the same SQLite transaction.

A canceled subscription produces `cancellation_review`, a past-due/unpaid subscription produces `payment_review`, incomplete Checkout produces `awaiting_payment`, and a failed remote check produces `unavailable`. The **projection count** then contains no candidate seats, but actual seats and member access remain unchanged; an unavailable check must not revoke users. A previously paid but now expired billing period is review-only. The Subscriptions UI keeps simulated seat candidates visually and semantically separate from real purchased seats and labels them *not purchased or activated*. Server-side aggregation is scoped to the currently selected organization.

This is NOT an entitlement engine. Before real billing, a separate reviewed migration must replace legacy additive receipts with subscription-based authoritative seats, define grace periods, reduce assigned seats safely, handle partial upgrades/downgrades/refunds/disputes and invoice ordering, integrate the six native apps, and pass end-to-end tests using an actual Stripe TEST account and staging backend. No production payment or user-license action occurs here.

## Read-only TEST seat transition impact and safe downgrades

Workspace also calculates a separate `testSeatImpact` diagnostic for administrators. It compares hypothetical TEST candidates with the existing per-app **assigned users plus reserved invitation seats**, and retains the real purchased seat count as a separately labeled reference. For an unambiguous, future-dated paid TEST candidate, a hypothetical shortfall is flagged as `assignment_conflict` if existing assignments plus invitations exceed the simulated seat quantity. For canceled, past-due, unavailable or expired TEST observations, it returns `manual_review` instead of recommending an automatic downgrade. Apps with no relevant TEST subscription have `not_evaluated`, never a zero-seat revocation instruction. The Subscriptions screen displays review warnings without changing membership, invitations, purchased seats or native app permissions.

This is **not** a command to enforce a reduction: the diagnostic sets `realSeatChanges: false` and `licensesGranted: false`. Production billing must separately define and test entitlements, grace periods, seat reservations, user notification and administrator-controlled resolution before any removal of existing access.

## Versioned shadow subscription entitlement ledger (no live effects)

The private database includes `subscription_entitlement_shadow`, an isolated, test-sourced record **keyed by Stripe TEST subscription ID**, with a unique organization/draft pairing and monotonic reconciliation revision. It is created **only after the original test subscription and paid invoice have been verified and linked**. A subsequent renewal of the same subscription replaces the record's revision and last paid invoice rather than creating additional licenses; a canceled, past-due or unavailable check replaces the recorded decision with a review-only state. All mutations occur inside the same SQLite transaction as the existing test observation. Prior invoices remain in the private test invoice-reference ledger for audit.

The pure `subscription-entitlement-planner.mjs` takes validated subscription records and organization app-seat assignments/reservations, and computes a **non-executing** per-app transition preview. It aggregates distinct subscription identities (not invoices), supports different app selections for Single/Mixed/Bundle, rejects duplicate subscriptions/foreign tenants/overflow, and reports `increase_candidate`, `unchanged`, `decrease_requires_review`, `assignment_conflict`, `manual_review`, or `not_evaluated`. Expired terms and unresolved states are never candidates. Every preview explicitly returns `realSeatChanges: false` and `licensesGranted: false`.

The shadow ledger does **not** update `seats`, `assignments`, `receipts`, authorization decisions or native apps. It is accessible only through private organization-store internals, not a public billing or purchasing route. It is preparation for a later reviewed production-entitlement migration, not its activation; there is no automated Stripe polling, real payment processing, app grant, cancellation, renewal or seat removal.

## Organization admin preview of shadow subscription transitions

The authenticated, CSRF-protected organization Subscriptions response includes `testEntitlementPlan` **only when the private Stripe TEST reconciliation feature is enabled**. It summarizes the read-only subscription shadow ledger for the administrator's selected organization: per-app simulated seat quantity, current real purchased seats, assigned users, invitation reservations and whether an increase is a candidate, a downgrade requires review, assignments exceed a hypothetical quota, or billing evidence is unresolved. The private Workspace Subscriptions screen displays this preview separately from real purchased seats and always states that no user access changes.

Unlike the legacy additive purchase model, the preview derives from unique subscription IDs and never treats repeat/renewal invoices as additional licenses. No new public route, Stripe API exposure, automatic user deactivation, seat write, app grant, or live billing authorization is created.

## Shadow entitlement inventory completeness (TEST only)

A paid-only shadow plan can omit Checkout sessions that have not yet produced a verified subscription. The additional private `testEntitlementReadiness` diagnostic therefore compares all **ready TEST Checkout drafts** with their test subscription shadow bindings before a manual reviewer interprets hypothetical subscription seats. It marks unbound Checkout sessions and subscriptions with unresolved or expired billing periods per app, and shows explicit review warnings in the administrator's Subscriptions page. `readyForManualPlanning` only means this **test-only diagnostic snapshot** has no detected missing or unresolved sources; it never authorizes activation or revocation of actual licenses. A provider outage or unverified payment always blocks readiness.

## Freshness guard for read-only Stripe TEST entitlement diagnostics

An earlier paid Stripe TEST check **cannot** be used as a current seat candidate while a more recent reconciliation is in progress, superseded, pending, or unavailable. The SQLite-backed TEST capacity estimate, subscription shadow planner, readiness report, review-impact report and per-draft seat preview all require the *latest* attempt to equal the stored candidate revision, have the `paid_test_verified` state, and have a completed timestamp not in the future or more than 24 hours old. The paid billing period must still extend beyond the current server time. Starting another check immediately invalidates the old positive candidate across all UI-facing summaries, including after a backend restart; a new verified paid check restores only a **test-only** candidate. Historical paid checks remain readable for auditing but never authorize actual seats. All legacy `seats`, receipts, invitations, assignments and native app access stay untouched. The 24-hour window is an intentionally conservative **diagnostic freshness limit**, not a Stripe payment or production license policy.

## Partial TEST billing inventory must not show actionable entitlement increases

The read-only subscription shadow plan is now cross-checked against the separate tenant-scoped Checkout-readiness inventory for each app. A previously paid TEST subscription can coexist with another **ready but unverified Checkout** for the same app; the paid-only shadow by itself is a partial inventory. In that case the plan and seat-impact status return `manual_review`, with `unboundCheckouts` and `unresolvedSources` diagnostics, even when the confirmed source contributes some historical candidate seats. The browser also shows an app with **only unverified Checkout sources** in the TEST preview as requiring manual review, instead of omitting it as `not_evaluated`. Once all sources are verified and fresh, the ordinary TEST-only candidate/downgrade analysis resumes. As before, none of these results activates, removes or changes real seats or permissions.

## Planned verified subscription seat transitions (not activated)

The new **pure** `verified-subscription-transition.mjs` module provides a billing-adapter-ready, non-mutating calculation for a future independently validated **live** subscription. Given a subscription's known previous revision, validated next revision, paid-through timestamp, Single/Mixed/Bundle app selection and live per-app purchased/assigned/reserved capacity, it computes exact per-app replacement deltas. An ordinary renewal produces **zero additional seats**; an upgrade is limited to the selected apps; downgrades and cancellation produce negative deltas only in the proposed transition. Existing legacy/manual seats in `seats.purchased` remain a separate component and are preserved by differential arithmetic.

The planner rejects non-monotonic or replayed revisions, mismatched organizations/subscription IDs, invalid app selections, missing/expired payment evidence for an *active target*, invalid cancellation attempts, capacity underflow and unsafe integer arithmetic. A reduction is **blocked for manual resolution** when the proposed purchased count would fall below existing app role assignments plus reserved invitation seats. The previous subscription's billing period may be expired when calculating its cancellation. All outputs explicitly indicate `realSeatChanges: false` and `licensesGranted: false`.

**Important boundary:** this is a pure library only. It does not verify Stripe signatures, call Stripe, persist subscription allocations, update `seats`, create/revoke users or enforce subscription cancellation. It must never accept untrusted browser input or be called from the TEST reconciliation path to grant access. A separate reviewed, authenticated billing authority, durable per-subscription ledger, atomic seat adjustment, idempotency and production policy must be developed and staging-tested before use.

## Private verified-subscription allocation ledger (not connected to live Stripe)

The organization store now has a **private, opt-in** `applyVerifiedSubscriptionTransition(evidence)` boundary. The store constructor must receive a trusted synchronous `verifyLiveSubscriptionEvidence` function which independently authenticates and normalizes **live** billing evidence. Without that dependency, every call fails closed with `verified_billing_unavailable`. A browser payload, public Checkout redirect, Stripe TEST reconciliation or unsigned webhook does **not** qualify. The existing private Workspace HTTP broker does **not** expose a route for this method and no production verifier is configured.

Only the verifier's normalized `source: 'stripe_live'` output, carrying an event key, exact organization/subscription identity, monotonic internal revision, plan, app selection, quantity, lifecycle state and paid-through timestamp, enters a single SQLite `BEGIN IMMEDIATE` transaction. The pure transition planner calculates per-app deltas against the current **live** purchased/assigned/reserved totals. A downgrade or cancellation that would leave fewer purchased seats than assignments plus pending invitations fails atomically with `verified_subscription_manual_review`, with no partial removal or status advance. A future billing integration must establish customer/payment ownership and a grace-period/notification/manual-resolution policy for blocked reductions.

`verified_subscription_allocations` stores one authoritative allocation per subscription ID, separate from the existing `subscription_entitlement_shadow` table used exclusively for TEST observations. `verified_subscription_revisions` records a canonical payload digest and unique event key per revision. Exact replay of the same event, or same revision with an identical payload, is idempotent; changed payloads with reused event IDs or revisions fail, and stale or cross-tenant updates are rejected. A normal renewal records its new revision with **zero seat delta**. All affected app seat counters, the new allocation/revision record and organization audit log update **within one transaction**, or all roll back. Legacy verified/manual purchases are preserved by applying only the subscription's delta to `seats.purchased`.

**Not activated in deployment:** There is no real Stripe verifier, trusted billing event consumer, recurring reconciler, signed webhook-to-entitlement bridge, customer data migration, administrator approval workflow or staging/live payment test. Tests inject a deliberately synthetic private verifier to exercise the ledger, not real money or test-mode access. Do not configure an identity/pass-through verifier in production or expose the allocation method as an arbitrary HTTP action.

## Read-only Stripe LIVE subscription/invoice inspection (no activation)

`stripe-live-readonly.mjs` is a **private, unconnected, read-only** LIVE billing observer. It accepts exclusively a private `sk_live_` key (never a TEST key), and a caller-supplied binding which **must first be loaded from an independently authenticated server-owned record**, not a browser request. That binding pins organization ID, Stripe subscription and customer IDs, recurring Price ID, plan, app selection and quantity. The adapter sends only GET requests to Stripe's subscription and latest invoice endpoints with a timeout, no redirects and bounded JSON. It insists on `livemode: true` across Stripe objects, exact metadata/tenant/customer/subscription/Price/quantity identity, a single licensed subscription item, no pending changes or paused collection, an active unexpired billing period, a paid (not externally marked paid) positive-value invoice, and an invoice line matching the **current** price, quantity, subscription and billing period (handling the current and legacy invoice/subscription API layouts conservatively).

Its only possible positive outcome is `candidate_for_manual_review`; this **cannot be passed to `applyVerifiedSubscriptionTransition`** because it is not a signed, revisioned live entitlement assertion, and always returns `licensesGranted: false` and `authorizesSeatChanges: false`. Missing, mismatched or uncertain data fail closed or produce a manual-review reason. In particular, a paid invoice alone is not sufficient for granting access because refunds/disputes, post-payment changes, proper private tenant binding, billing event authenticity, monotonic revisions, notification and grace periods remain unresolved. As of this commit there is **no private live Stripe key configured**, no operator scheduler, no authenticated source of persisted live bindings, no activation bridge or browser route. Synthetic fixtures do not contact Stripe. Never substitute a pass-through verifier in the private store, expose live keys to the client or construe this code as production payment readiness.

## Detached signed Stripe LIVE webhook verifier (metadata only)

The separate `stripe-live-webhook.mjs` module can verify a configured **private Stripe LIVE endpoint signing secret** against a raw, unmodified request-body Buffer. It accepts a maximum 64 KiB payload, one timestamp within five minutes of the server clock, and one or more valid HMAC-SHA256 `v1` signatures, comparing MACs in constant time. It only accepts `livemode: true` at both event and nested resource level, rejects Connect-account attribution, and requires the expected resource ID family for a narrow list of invoice, subscription and Checkout events.

The result is immutable and contains **only** event ID, type, resource ID, creation time, raw-body SHA-256 digest, `mode: 'live'`, `licensesGranted: false` and `authorizesSeatChanges: false`. No raw Stripe payload, payment method, customer details, external event actions or user entitlements are returned. A signed `checkout.session.completed`, `invoice.paid` or `customer.subscription.updated` event is **not independently proof of a settled, undisputed subscription**. The verifier is NOT wired to any HTTP ingress, stored ledger, background process, live billing reader or license allocator.

Stripe TEST and LIVE endpoint signing secrets use the same `whsec_` prefix: administrators must ensure the configured secret is from the actual **LIVE** webhook endpoint, rather than relying on the string format to distinguish them. This module checks the signed event's LIVE flags, but cannot itself guarantee how a signing secret was provisioned. It does not provide durable event replay detection beyond the five-minute signature window; a separate idempotent private ledger, on-demand Stripe LIVE customer/invoice/charge/refund/dispute revalidation, binding ownership checks and monotonic subscription revisions are necessary before any live entitlement changes. Synthetic tests do not contact Stripe or expose keys.

## Private DuckBio owner control panel (read-only)

When `SUITE_OWNER_ACCOUNT_ID` is configured in the private server environment to the **exact immutable central admin account UUID**, the designated active central administrator alone may open `/owner` and read `GET /api/suite/owner/overview`. Both centralized administrator status and the exact configured account ID are required on *each request*. The owner API is disabled by default without that setting. This special route is separate from and does not reactivate the legacy `/api/suite/admin/*` identity-grant paths that remain blocked in organization mode. It uses existing session authentication, sends `Cache-Control: private, no-store` and deliberately exposes **no write controls**. An organization administrator is never an owner by virtue of their organization role.

The private snapshot includes total organizations, distinct organization members and active memberships, central account identities, per-organization member/admin/invitation counts, real purchased/assigned seats by app, verified subscription allocation ledger (plan, apps, seats, status, revision, paid-through), clearly marked **unpaid TEST subscription drafts**, and a chronological cross-organization timeline drawn from the existing transactional `organization_audit` entries. Activity output excludes raw JSON details and sensitive payment references, returning only a whitelisted subscription revision/seat delta summary where relevant. Tables are bounded and report truncation. The owner page uses `textContent` to render dynamic data, not injected HTML. The snapshot has no payment collection or mutation API.

The financial section explicitly marks actual Stripe revenue, MRR, refunds and disputes as **unavailable** until a separate production billing ledger can provide reconciled numbers; existing TEST observations and subscription drafts must not be counted as revenue. Owner email alert delivery is **not yet activated** by this dashboard. Keep `SUITE_OWNER_ACCOUNT_ID`, session secrets and organization databases private, and do not mistake a central admin's access to this operational snapshot for access to a native app's scientific data.

## Opt-in owner change alerts via durable private outbox

Large organization and user changes can now generate owner e-mail alerts, but **only when explicitly enabled** in the private server environment. Set `SUITE_OWNER_ALERTS_ENABLED=true` along with an exact `SUITE_OWNER_ACCOUNT_ID`, verified `SUITE_OWNER_ALERT_FROM` sender, `SUITE_OWNER_ALERT_EMAIL` recipient, private `SUITE_RESEND_API_KEY`, a configured `SUITE_ORGANIZATION_DB_PATH` and HTTPS `SUITE_ORIGIN`. When disabled (the default), no owner alerts are enqueued or sent and the owner panel reports that delivery is off. All of these values belong in private server configuration, never GitHub Pages or public scripts. Invitation emails are separately opt-in with `SUITE_INVITATION_FROM` and do not silently activate just because an owner notification sender is configured.

The existing transactional organization audit now records **subscription draft created/canceled** events and provides the owner timeline across organizations. A conservative subset of major events is separately queued when owner alerts are enabled: organization created, member added/removed/activated/deactivated, member role/admin changed, invitation accepted, app permission changed and **verified subscription entitlements actually changed** (or were canceled). Normal paid subscription renewals with zero seat change remain in the audit log but **do not** generate a major-change email. Stripe TEST Checkout and reconciliation events never generate owner alert emails.

The private SQLite `owner_alert_outbox` table is joined to a unique organization audit entry and committed with that audited change. A private dispatch worker starts **only after the broker server begins listening** and, when configured, checks the queue at most once per minute, up to 10 messages per pass. Workers lease rows transactionally for two minutes, preventing competing processes from sending the same row simultaneously. On transient email provider failures the event remains queued with bounded exponential backoff, up to six total attempts; unresolved failures appear as `failed` in the owner dashboard. A stable `duckbio-owner-audit-<audit ID>` provider idempotency key protects retries and ambiguous acknowledgments. Successful Resend API acknowledgment is displayed as `sent` in the outbox, but this is **not confirmation of inbox delivery**.

Alert email bodies contain a short action description, organization, timestamp, actor and target account identifiers and optionally a per-app seat delta/revision, plus a link to `/owner`. They deliberately omit passwords, invitation activation URLs, webhook payloads, raw Stripe receipts, payment details and credentials. The owner dashboard summarizes pending/sending/sent/failed counts. This is operational activity notification, **not** an independent Stripe billing or security monitoring system; failed login attempts, chargebacks and refunds are not yet integrated and therefore cannot trigger these alerts. Tests mock Resend and do not actually send email. Real mail will start only once the private production server is deployed with an explicitly enabled verified sender and recipient.

## Durable Stripe LIVE signed-event metadata ledger (unassigned, no activation)

The private SQLite `stripe_live_event_log` records **only** normalized metadata previously returned by the separate raw-body, signed LIVE webhook verifier, via the **private** `recordVerifiedStripeLiveEvent` method. No HTTP route, auto-processing worker or public access has been added. The method requires LIVE mode, expected Stripe event/object ID families, valid timestamps and a SHA-256 digest; a repeated event ID with exactly matching normalized metadata is a no-op. Reusing an event ID with changed digest, type, object or timestamp fails closed, including after database restart.

An event is deliberately **unassigned** to any organization. In particular, a signed invoice or Checkout completion is not itself proof of an owned, paid subscription, nor may the handler infer a tenant from arbitrary Stripe metadata. The owner-only private dashboard displays the total LIVE event count and the most recent 100 *types/timestamps only*, explicitly marked awaiting reconciliation, without exposing raw payloads, customer identifiers, invoice IDs or sensitive metadata. The audit log for organization and user changes remains a **separate** source from the Stripe provider event ledger.

The new ledger never calls the verified subscription transition writer, modifies seats, changes permissions or triggers owner notification emails solely because a webhook arrived. End-to-end production integration requires a reviewed and configured LIVE ingress endpoint, durable organization-to-customer/subscription bindings, server-side Stripe invoice/payment/refund/dispute reconciliation, idempotent subscription revisions and staging verification. Synthetic tests use only in-memory signed fixture payloads and a private SQLite database; they do not contact Stripe.

## Internal chat and virtual DuckBio mail (private beta)

The private broker may optionally enable messaging with `SUITE_COMMUNICATIONS_DB_PATH`, an **absolute private** SQLite database path separate from identity, org membership and business-data files. Without that setting the communications APIs remain unavailable. The `/messages` Workspace interface provides two distinct channels: lightweight Messenger-style, direct user-to-user chat refreshed by **five-second bounded polling** (not WebSockets or guaranteed push), and an internal mail inbox/sent view with subject, body and read markers. Text is stored privately in SQLite; there is **no external SMTP/IMAP server, MX record, mailbox or public email routing**. Never mistake these virtual addresses for internet addresses.

A private `virtual_addresses` table assigns each active account a persistent random `duck-<24 hexadecimal characters>@duckbio.internal` address on first use. The only reserved owner mail aliases are `support@duckbio.internal` (user mail to the explicitly configured owner account) and `billing@duckbio.internal` (private system subscription notices to the same owner). Internal addresses have no external delivery. The system-only API `postSubscriptionNotice` is available for future verified subscription change integration and `postSecurityAlert` for internal owner security chats, with durable reference-based idempotency. **These private system hooks are not yet wired to billing/security detection** and cannot be invoked over any user-facing HTTP route.

Organization contact books are derived from active memberships, with no native scientific app access or exposed real email. Users can also search **other organizations' active members** by DuckBio display name or known virtual address; queries return bounded results without real email addresses. The central account specified by `SUITE_OWNER_ACCOUNT_ID` is **excluded from all user chat search and contact-book responses**, even when it belongs to their organization. Regular users cannot send chat to this owner account, including by guessing its internal account ID, and cannot send to the reserved security system sender. Only the central owner can initiate chat with regular users; users may send the owner **internal mail only through the support alias**. The billing alias is restricted to system notices. The owner can receive dedicated security alerts in the private chat from the system sender, not from regular users.

All user-facing communications endpoints require the existing authenticated **active** central identity and an active organization membership (or the exact central owner identity); POST endpoints use the established CSRF protection. Recipients must be active and belong to at least one organization, subject to the owner mail-only restriction. Messages are limited to 2,000 chat characters, 160-character mail subjects, and 8,000-character mail bodies. Private SQLite enforces stable send idempotency via sender/client ID and a basic 20-messages-per-minute-per-channel throttle. Browsers render message contents via `textContent`, not raw HTML. The first implementation deliberately omits attachments, file sharing, group chat, reactions, arbitrary HTML, push servers and federation; it is meant to stay lightweight.

Future work includes operational retention and deletion policies, abuse-reporting/block lists, more granular cross-organization discovery preferences, security event detection, actual billing-to-internal-mail delivery, public contact-form dual routing, and separate **tenant-isolated user LLM** versus **owner-only LLM** services. No LLM should receive another organization's data or private owner operational data without independently enforced server-side authorization, and no customer content may be used for third-party model training without an explicit reviewed agreement.

## Automatic private owner billing mail and security chat from audited events

When both `SUITE_COMMUNICATIONS_DB_PATH` and the exact `SUITE_OWNER_ACCOUNT_ID` are configured on the running broker, a **private SQLite-only** worker runs on startup and at a bounded 15-second cadence. It reads the existing transactional organization activity journal in ID order and dispatches **verified subscription allocation transitions** to `billing@duckbio.internal` as internal mail. Independently, real audited **administrator promotions**, acceptance of an organization-admin invitation and enabled app permissions appear as security-relevant alerts in the owner's `DuckBio Security` chat. These are **audit facts**, not assertions that an external attack occurred.

The separate communications SQLite database persists a monotonically increasing processed-audit ID; notices and chat messages are keyed to the audit ID and deduplicated. If a process restarts between creating a notice and updating the watermark, replay returns the existing notice rather than sending a second one. If delivery fails, the cursor is not advanced past the failed record; a later pass retries. Disabling communications stops dispatch but does not delete the organization audit entries.

Neither the contact form nor Stripe LIVE webhook signatures constitute verified billing changes, so **TEST checkout events, unsigned payment events, unrelated organization mail and user messages cannot manufacture billing notifications**. A valid subscription revision stored through the independently verified private subscription ledger does create an owner billing notice. Current security coverage is limited to the meaningful permission/administrator changes recorded in the organization audit; login threats, rate-limiter attacks, database intrusion and cloud infrastructure alarms still require reviewed event producers and alert policy. This bridge never sends external email and never grants or removes licenses.

## Public website contact form to owner internal inbox AND real email (deployment-gated)

A separate **opt-in** public contact service now accepts JSON at `POST /api/suite/public/contact` from exact allowed HTTPS marketing-page origins. It is **disabled by default**; enable only with `SUITE_CONTACT_ENABLED=true` and verified private configuration:
`SUITE_OWNER_ACCOUNT_ID`, `SUITE_COMMUNICATIONS_DB_PATH`, `SUITE_CONTACT_TURNSTILE_SECRET`, `SUITE_CONTACT_ALLOWED_ORIGINS_JSON` (e.g. `["https://dennisbsj.github.io","https://duckbio.net"]` after those hosts are controlled), `SUITE_RESEND_API_KEY`, `SUITE_CONTACT_FROM` (verified Resend sender) and `SUITE_CONTACT_REAL_EMAIL` (actual external owner inbox). The server validates the actual Turnstile result and permitted hostname, exact Origin and Host, bounded JSON input, private data types, duplicate submission keys and sender/global hourly limits. This does **not** rely on a real email mailbox for any internal DuckBio address.

After a valid submission, the private communications database transaction first creates a permanent **internal** owner mail at `support@duckbio.internal` (kind `contact`), then adds a **durable outgoing real-mail job** with stable idempotency reference. The public response is HTTP 202 with `accepted:true,internalDelivered:true,externalStatus:'queued'`: it does not pretend that an external mailbox has received the message. Public contact messages are owner-only, never searchable as other users, and are not a permission or billing event. Real vendor verification and anti-spam load tests are required before launching an anonymous production endpoint.

## Private internal messaging foundation (backend only)

`private-messaging-store.mjs` introduces a small, private SQLite data layer with two message kinds: `chat` (short instant messages) and `mail` (subject + body in a lightweight internal inbox). Each active central user receives a deterministic, unique **internal alias** in the reserved fictional `@duckbio.internal` namespace, derived from their immutable account ID. This is NOT an externally routable email address and needs no SMTP server, MX record, email account or separate mailbox provider. Internal mail is stored as rows associated with sender/recipient identity IDs.

The backend enforces asymmetric owner communication using the separately supplied, immutable `ownerAccountId`: normal users cannot send *chat* to the owner, while the owner can initiate chat with any active user. Users may send **internal mail** to the owner. Accounts must be active and are looked up through a trusted central identity resolver. Operations include idempotent sends, conversation history, mail/chat inbox, read receipts and a coworker-only contact directory supplied by a trusted organization membership resolver. Cross-organization messaging by previously resolved account ID is supported. Directory-wide cross-organization **search is not yet implemented** and should be privacy-aware, rate-limited and opt-in before exposure.

**Not connected to Workspace UI or HTTP yet.** The code is a tested backend foundation only; no production messages are delivered and the current admin Workspace communication interface is unchanged. Before launch, connect these functions to authenticated session-bound routes with per-user rate limits, contact discovery controls, reporting/blocking and anti-spam protections, message retention policy, chat polling or WebSockets and secure notification handling. Any **owner security notifications** must be generated by separately verified security events through a system sender, not by ordinary user-to-owner chat. Automated subscription change mail needs a separate trusted system mailbox writer; it must not simply treat user-crafted messages as billing evidence. LLM assistants are separate future modules and must never access cross-tenant private data through these messaging functions.

## Globally unique IDs for DuckBio samples, documents and workspaces

A new **private** `content-id-registry.mjs` creates a single SQLite **AUTOINCREMENT** sequence for file-like objects across **all six apps**. The human-readable ID consists of an app prefix and a zero-padded global sequence, for example `ld000001` (LabDuck), `dm000002` (DuckMan), `dn000003` (DuckNote), `cd000004` (CytoDuck), `md000005` (MethDuck) or `dt000006` (DuckTrain). Because the sequence is **global**, no two registered resources – even from different apps – share the same numeric serial or complete ID. Content names are likewise globally unique after Unicode NFKC normalization, case folding and whitespace normalization, including across organizations. Names and numbers remain reserved on archival (there is deliberately no hard-delete method). Native resource keys are idempotent and unique for a given app/organization.

The registry is **not open to user-initiated API requests**. A private app backend must independently attest that a source object exists and that it is allowed to register it; the supplied `verifyRegistration` callback is mandatory. Resource metadata is returned for an `@ld000001`-style mention **only if a separately supplied native-app `canView` verifier authorizes the specific viewer**, otherwise the result is indistinguishable from a nonexistent ID. No app-scoped permission or token is inferred from the mention itself. Mention parsing extracts distinct IDs from text; the message layer must resolve only for authorized recipients. This first increment is the shared backend registry; app migration, exact owner UI links and content-rich previews are not yet connected. A single persistent database must serve all apps; independent per-app copies would break global uniqueness.

## Group chat, group mail and typed mentions

The already deployed-code-bound `communications-store.mjs` and private `/messages` client now support **group conversations** alongside direct messages. A group has a title, a selected list of 2–29 additional account participants, either `chat` or `mail` semantics, and its own persistent message history/read receipts. Group membership is checked server-side on every group read/send; no user can access another group's history by guessing its ID. Group creation requires a valid authenticated session, CSRF protection and each member's verified active central DuckBio account with current organization membership. Members may belong to *different* organizations. Group creation/send requests have private idempotency keys and existing per-sender message throttling applies. Group members are fixed at creation in this first implementation.

**Owner communication restriction:** an ordinary user cannot create an instant-message group including the central DuckBio owner, nor can they send chat in an owner-containing group created by the owner. The owner can create such a group and broadcast chat messages; everyone can read them. Group **internal mail** may include the owner and allows members to send mail replies, consistent with the existing owner support mailbox rules. A group mention never adds new members automatically.

Unique account mentions use a stable literal `@u-<hex-encoded-account-ID>` token, inserted by the UI's "Tag" buttons; contents such as `@ld000001` or `@dm000002` use the shared resource prefix registry. Both group and direct chat/mail store these as **plain text references**, with safe structured extraction. User tags outside the private conversation are rejected rather than exposing third-party account activity. Reference styling is text-only; **no resource title, direct file URL, or access is provided by the text alone**. The separate content ID registry's native permission verifier must be connected to each app before the client may display clickable resource links, previews or search suggestions. Native app data migration and historical ID assignment remain open work.

The UI allows selecting participants from coworker contacts and global DuckBio user search, creating chat or mail groups, writing/reading group messages, and inserting unique user tags. UI and server use text-only rendering for untrusted message bodies. Production configuration, native-file deep-link routing, real-time WebSockets and content-specific access tests remain separate follow-ups.

## Private @mention activity

Users tagged with their stable `@u-<hex>` account handle in an authenticated direct chat, internal mail, group chat or group mail receive an in-app **Mentions** entry. These records persist in the private communications SQLite database and are keyed uniquely by recipient + message source + message ID, so retries cannot generate duplicate alerts. The recipient's central identity must be part of the relevant direct correspondence or existing private group; typing another person's handle does **not** add them to a group, open their inbox or grant access. A mention notification includes only the sender identity reference, message/group reference, timestamp and read state, and is returned solely to the signed-in mentioned account via a no-store API. Account-scoped read marking is idempotent. The UI polls existing in-app messages and mentions without a push provider and can navigate to the relevant conversation.

Owner-initiated group chat announcements are explicitly **read-only** for ordinary members; the server returns a separate `canSend` flag and the UI disables the reply control. The normal owner restriction is enforced on the server even if a client forges another value. The owner can still receive internal mail. Resource `@ld...` etc. tags do not create mention notifications; native app permissions must be connected before displaying clickable links or previews. No external email, WebSocket or production deployment is part of this increment.

## Unified Notifications, co-author events and unread communication launchers

The separate `Mentions` panel is renamed **Notifications**. The owner-scoped/private communications database aggregates personal @mention events and explicitly verified native-app **co-author assignment notifications**. `postCoauthorNotification` is private-server-only, accepts a unique source event key, recipient/actor/app and globally registered app-prefixed content ID, and is **disabled unless a trusted `verifyCoauthorEvent` callback** is configured; no user or browser endpoint can mint a co-author event. This callback must independently establish authenticity, active membership, and native content access; an ID alone is never permission. Duplicates cannot create extra notices. Each user sees only their own inbox and may mark only their own notices read. Notification display opens an app content launch path in a new tab; until the native resource authorization/redirect adapter is configured this path must remain inaccessible, not bypass an app login. Browser preferences may render popup windows as tabs. This script is only served from the authenticated Workspace origin; native apps on independent origins still require a separately integrated, authenticated launcher. **No cookies, tokens or sensitive cross-origin message counts are exposed** through a public embed. ## New-tab web links and native app content gateway

Internal messages render HTTP(S) and www. URLs as clickable links targeting a new tab with noopener, noreferrer and no-referrer attributes. Untrusted HTML is never interpreted. DuckBio object references such as @ld000001 similarly open a new tab, but target the authenticated same-origin /content/ld000001 gateway. Only safe http/https external links and recognized app content ID prefixes become links.

The gateway requires a valid Workspace session and an independently verified, private resolveContentResource adapter; it is disabled by default. The trusted adapter must verify native object existence and the user's permission to view it. The gateway separately verifies the active organization app assignment, exact app prefix, registered native HTTPS origin, and strict /content/<ID> destination path without query, fragments or credentials. Unknown IDs, missing adapters or inactive access return no content URL. An unauthenticated visitor is directed to Workspace login.

The native apps still must register their objects in the shared content ID registry, implement the native /content/<ID> handler and verify their own session and per-resource permissions. Workspace does not mint native-app cookies, sign in as a user, or grant access via hyperlinks. Once those integrations are connected, an already valid remembered native app session permits immediate opening; otherwise the app must require its own login. Browser settings determine whether a requested new window or tab is used. The co-author notifications use the same secure gateway.

This PR contains the link UI and protected gateway, not live native app integration, production deployment, or actual bypass-free native app session testing.

## Workspace Remember me and session expiry (local private identity)

The private Workspace login now has an explicit **Remember me on this device** checkbox. Without it, the identity session has a finite eight-hour server-side validity and uses a **browser-session cookie without persistent Max-Age**, so normal browser closure ends the browser's usable session. With explicit opt-in, it uses a persistent **fourteen-day** private identity session and an equally bounded HttpOnly, Secure (except localhost), SameSite=Lax cookie. Both are server-revocable immediately on sign-out, password change and account deactivation. The server never persists plaintext passwords, and the browser never receives the session secret through JavaScript. No localStorage tokens are used. Existing signed-in sessions remain valid only until their server-side expiry.

This implementation covers the **private Workspace identity cookie only**. It does not force other DuckBio apps, on different HTTPS origins, to retain login or share cookies. Each app needs the same explicit remember-choice/session-expiry behavior at its own authentication boundary before native deep links can open immediately without asking for login. Opening a content link never bypasses the destination app's session or resource permissions. A normal non-remembered session can still be shared among tabs while its original browser session remains open; closing the browser or the finite expiry requires reauthentication. Browser private-browsing and cookie settings may shorten the session.

## Content-link login continuation (Workspace gateway)

An unauthenticated request for a syntactically valid global resource URL (`/content/<app-prefixed-ID>`) now redirects to `/workspace?content=<ID>` rather than dropping the requested object. After the account is authenticated, Workspace accepts only **one** ID matching the six recognized prefixes and numeric suffix; it verifies the central account before navigating back to the same-origin protected `/content/<ID>` gateway. Already-authenticated, including remembered, Workspace sessions can resume immediately. Arbitrary callback URLs, external redirect destinations and duplicate `content` parameters are never accepted as continuations.

The private gateway still checks current Workspace organization/app access and a separately configured native resolver before emitting an HTTPS native-app content URL. **This is not native app SSO or native object authorization**: the destination app must independently check its own session and object permissions, and may require its own login. Browser regression tests use a synthetic native destination and do not claim a deployed native integration.

## Chat, mail and Notifications login continuation

Opening the private `/messages?view=chat|mail|notifications` communication window without a valid Workspace session now takes the user to `/workspace?messages=<view>`. After the normal central login, the requested **allowlisted** view opens automatically; users with an existing remembered Workspace identity can resume without reauthentication. Duplicate parameters and arbitrary URLs are rejected as redirect destinations, and an unknown incoming view defaults to chat. ## Native app unread counters — private server-to-server bridge (source only)

The private Workspace broker exposes `POST /api/suite/native/communications/unread` for an explicitly registered native app backend. It takes **only** `{"sessionToken":"<opaque broker proof>"}` in a JSON body and the existing app's **server-side** HTTP Basic client ID/secret (the same registered identity used for broker exchange/introspection). It returns `{"counts":{"chat":N,"mail":N,"notifications":N}}` with `Cache-Control: private, no-store`, and never responds with an app/Workspace cookie, raw communication content or another user's account ID. The counts belong exclusively to the current central identity bound to that client and live broker proof.

The broker rechecks the **current** parent session, password-change state, exact app identity mapping and app grant before returning a central identity. Workspace independently requires an active identity and current organization membership **plus a current assigned role for the requesting app in the explicitly bound organization** (or the exact eligible owner). Native grants without an organization binding cannot borrow rights from any other membership. Invalid/expired/wrong-client proofs and revoked access fail closed. Arbitrary user ID, Origin/browser requests and cookies cannot be substituted for a server-held broker proof. No external CORS access is enabled.

**Native app integration is still required:** each app backend must first authenticate its *own* native user session and prove that the broker proof belongs to the same linked local user before calling this endpoint. It must never expose the registered client secret or opaque proof in HTML, JavaScript, localStorage, URLs or public logs. The app may return only the three counters to its already authenticated native browser frontend after its own permission checks. Use bounded polling and stop displaying counters when the proof becomes invalid. Broker exchange proofs have their existing finite life (normally at most eight hours), even if the separate native app Remember me cookie lasts up to fourteen days; this route does **not** renew a proof, mint SSO, link accounts by email or grant access to content.

The bridge is deliberately **read-only**; it cannot send messages, mint co-author events or register content IDs. The code and synthetic regression tests alone do not mean the six apps currently call it, or that any native login is deployed. No app changes, DNS, payment activation or production deployment are included.

## Registered native-app connection page (source only)

Workspace now serves `GET /connect?appId=...&redirectUri=...&state=...&codeChallenge=...` for a native app backend that has **already** created a high-entropy PKCE verifier and one-time state bound to the app's current authenticated local session. The Workspace server permits this screen only when the query has exactly the four documented parameters and the callback URL is **exactly** one registered for that app. Duplicate parameters, unknown apps, unregistered callbacks and unsafe PKCE values fail closed with HTTP 400. The first-party page uses the existing browser CSRF session and central account, asks for explicit continuation (or credentials when no central session exists), and calls the existing broker `authorize` or `login` endpoint. The broker independently checks live app grants and returns only a one-time authorization **code** in the native callback URL. The central password, CSRF token, client secret and broker proof are never sent through the callback URL. The app must exchange the short-lived code on its **backend** using the registered client secret and PKCE verifier, then check that the broker assertion's `localIdentity.userId` and `organizationId` match its **still-active** native session before storing any proof. Never link native accounts by email or infer native roles from central ownership.

This is a **necessary browser-side authorization entrypoint**, not a completed native app backend implementation: none of the six apps has yet added a PKCE initiation/callback, server-held proof, validated native-user binding or the secure unread-counter polling requested by the Workspace bridge. An existing native Remember me session does not automatically authenticate the central account. No production domain, external provider, deployment, payment or bulk migration was changed. Tests use only synthetic local browser/server data and intercepted fake native callback hosts.
